# AI 审查工作流的依据与适用边界

核对日期：2026-10-23。本次为工作流改进的定向检索，不是系统综述，也不宣称覆盖全部最新研究。

## 从现有流程保留什么

保留 Issue 范围锁定、Design/Work/Review 分工、只读审查、候选证伪、稳定 RV ID、有限返工和基于实际证据的合并判断。提示词本身不授权消息发送、代码修改或合并；每次动作以用户实际授权为准。

## 研究依据与工程选择

| 来源与核对范围 | 支持的判断 | 本仓库采用的规则 | 限制 |
|---|---|---|---|
| Konstantinou, Tambon, Papadakis, 2026，[On the risk of coding before testing](https://arxiv.org/html/2607.05139v1)，核对摘要及研究设计 | 生成的实现可能把错误传递给后续测试 | 先记录验收与独立 oracle；核对回归测试是否区分错误行为 | arXiv 预印本；编程任务实验不等于安全协议或闭环控制的正确性证明 |
| Li 等，2026，[Independent Patch Verification…](https://arxiv.org/html/2608.08950v1)，核对摘要及 RETRACE 方法 | 可以从需求和补丁分别重建目标并检查偏离 | Review 分开概括契约与实际改动，核对二者 | 本流程不隔离原始 Issue 上下文，不是原论文的盲审实验，也不承诺同样增益 |

上述方法只用于提高发现问题的机会。数学/协议结论仍需原论文前提、推导和可执行证据；固定 seed、测试通过、多个 AI 意见一致，都不能替代这些依据。没有新增模型调用、服务依赖或自动执行器。

## 本次修正的具体缺口

1. 原 Review 的证据排序把实现放在 authoritative requirement 之前，容易把“已经这样实现”误作“应该这样实现”。现在分开判断契约与事实。
2. 现有测试清单已有 expected 独立性要求，现把它前移到 Design 验收矩阵，并补充 oracle 来源和未执行状态。
3. 将验证绑定到 SHA、配置、环境和工作区差异，复核 head/base 变更，避免复用过期 PASS。
4. Confidence 数字只表示主观判断，不声称经过概率校准；合并仍依赖完整证据。
5. 纯 Markdown 任务采用路径、链接、命令和规则一致性检查。运行逻辑或配置变化仍执行项目完整验证；不会为了“全绿”降低验证要求。
6. 修正文档示例中 Python `round` 与论文 `floor(x+1/2)` 规则的冲突；正式编码继续使用现有实现。
